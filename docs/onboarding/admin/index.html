Standing up the hosted simulator for interview season

Keys in, accounts made, cohorts ready, and nothing shared that should be private

The admin owns the deployment and the people in it. This guide goes from the environment variables that make the interviews work, through creating instructors and challenger cohorts, to the dashboard tabs you will use every week.

    01

    Become the first admin

    Where: the server's environment, then /login

    Accounts live in Firebase Authentication; roles live in the simulator's own user directory. The very first admin is promoted by email at boot:

    AUTH_BOOTSTRAP_ADMIN_EMAIL=you@yourschool.edu
    1. Set that variable on the deployment (Railway → your service → Variables) and redeploy.
    2. Create a Firebase user with the same email in the Firebase console (Authentication → Users → Add user), or sign in once through the app's sign-in page after the account exists.
    3. Sign in at /login. The first sign-in with that email, while no admin exists yet, makes you admin. The menu bar then shows Dashboard, which goes to /admin.

    The dashboard opens on Overview: people by role, cohorts, sessions with how many are active, submitted, in progress or not started, coverage meters for personal Groq keys and GitHub tokens, a 14-day activity chart, sessions by scenario and level, and the most recent sessions.

    Only the first admin needs thisFurther admins are created from the Users tab like anyone else, with the role set to admin. Remove the bootstrap variable afterwards if you like; it only acts while no admin exists.

    03

    Create instructors and challengers

    Where: Users

    One form creates an account: name, email, an optional password, a role (challenger, instructor, admin), and optionally a cohort. Leave the password blank and the person receives a set-password email with a link to choose their own; that is the normal path.

    • Instructors get the instructor dashboard and see only the sessions they create.
    • Challengers get a dashboard listing the sessions assigned to them and a Settings page for their name and personal keys.
    • Edit changes name, email, password, role, or cohorts. Delete removes the account from both the directory and Firebase.

    The Keys column shows, for each challenger, whether they have saved a personal Groq key and GitHub token (green with a tick). The Show filter above the table narrows the list to challengers missing one, which is the list to chase before a class.

    Bulk import

    Bulk import… takes a pasted list, one person per line: an email, Name <email>, or rows copied straight from a spreadsheet. Existing accounts are reused. Keep Email each new account a set-password link ticked so people can sign in without you handing out passwords.

    Firebase's email quotaSet-password emails are sent by Firebase, which allows 150 per project per day on the free (Spark) plan and 10,000 with a billing instrument attached (Blaze). Test sends, resends and "Forgot password?" all count. Past the limit, rows fail with QUOTA_EXCEEDED : Email quota exceeded; the Firebase account is created but the person is not saved in the simulator's directory, so delete them under Authentication → Users in the Firebase console and import them again once the quota resets or after moving to Blaze. Current usage is under Google Cloud console → IAM & Admin → Quotas, filtered on "Identity Toolkit". For a class of more than a hundred, attach billing before import day.
    Resending a linkOpen a person's Edit panel and press Send reset email. That is the answer to "my email never arrived".
    Create instructors firstCohort sessions are created by an instructor, so at least one instructor account must exist before class day. Make yourself one if you are also teaching; an admin can use the instructor dashboard directly.
    04

    Group challengers into cohorts

    Where: Cohorts

    A cohort is the unit instructors schedule against: one click creates an interview session for every member. Two ways to build one:

    1. New cohort from a pasted list… Name the cohort, paste the class list, and the accounts are created (or reused) and added in one go. This is the fastest route from a roster to a ready class.
    2. Create an empty cohort, then Open it and add members from the directory, or use the bulk box on the cohort page.

    Inside a cohort you see the member list with Remove per person. Deleting a cohort does not delete its people.

    05

    Curate the scenario list

    Where: Scenarios

    Every scenario folder in the repo appears here with two controls:

    • enabled: untick to hide a scenario from instructors' New session lists. For interview season, keep the twenty iv_* scenarios on and hide the rest so the list stays short.
    • starter URL: the public GitHub repo hosted learners fork for a build scenario. Interview scenarios leave this blank; they are edited and submitted in the browser. The instructor publishing steps are in docs/PUBLISH-SCENARIOS.md.

    Scenarios are data. Adding one is a new folder with a scenario.yaml and a starter/; the iv_* set is generated by tools/write_interview_scenarios.py, so edit the script rather than the YAML.

    06

    See every session, and clean up

    Where: Sessions

    The admin list shows all sessions across all instructors: owner, assignee, scenario, level, status, message count, last activity. Replay via instructor opens the same replay view instructors use, including the drawn design diagram and grading. Delete removes the session and everything attached to it: transcript, unlock state, mail, tickets, submissions, browser-edited files, and its workspace folder.

    Delete is permanentThere is no undo and no archive. Export the session from the instructor replay first if you want a record.
    07

    Settings: a health line and one default

    Where: Settings

    Four cards, plus a read-only Deployment panel.

    • Classroom defaults. The engineer level a session gets when the instructor sets none (senior is the usual choice), and a one-line announcement shown as a banner on every challenger's dashboard. Blank hides it.
    • Sign-in. Whether the sign-in page offers Create challenger account. Turn it off once your cohorts are imported: unknown emails are then told to ask their instructor, and only accounts you created can sign in.
    • Grading. Whether grades carry the "directional, not calibrated" caveat. Follow the environment variable, or override it here. Only choose Yes after the calibration harness has been run against real instructor scores.
    • Deployment. Read-only: model and provider, whether the classroom Groq key, GitHub token and key-encryption secret are set, work mode, sandbox, public URL and bootstrap admin. If it shows password or sqlite on the hosted URL, the environment variables from step 2 are not being read.

    Recount dashboards now clears the overview and session-list caches; they otherwise refresh themselves in the background about once a minute.

    08

    Keys, rate limits, and letting people bring their own

    Where: Railway variables, plus each person's Settings

    The server has one classroom key per external service. Each challenger can add their own in Settings; the simulator then uses that person's key for their sessions and falls back to the classroom key for everyone else. Keys are validated on save, encrypted with BYOK_SECRET, and never displayed again.

    ServiceClassroom keyPersonal keyGet one
    Groq (language model)GROQ_API_KEYSettings → Groq API keyconsole.groq.com/keys
    GitHub (build scenarios)GITHUB_TOKENSettings → GitHub tokengithub.com/settings/tokens, see GitHub's guide. No scopes needed.

    For an interview-only season the Groq key is the one that matters: every persona reply, reveal judgment, diagram, and grade is a model call, and a class submitting together is the peak. Ask challengers to add their own key before the day; the challenger guide walks them through it. The Overview's coverage meters and the Users tab's Show filter tell you who still has not.

    09

    Make the set-password emails read like yours

    Where: a terminal with the service account, or the Firebase console

    New accounts get Firebase's password-reset email. A small tool reads and updates its sender name and subject:

    python tools/email_templates.py show python tools/email_templates.py apply --app-name "Your course name"

    The daily sending limit from step 3 applies to these emails too; the plan, not the template, decides how many go out.

    Firebase only honours a custom message body once a sending domain is verified under Authentication → Templates in the Firebase console; until then the stock body is used and the tool says so. The link inside always returns people to your /login because of PUBLIC_BASE_URL.

    10

    Before the season: a checklist

    Run through once, a week before the first cohort
    1. Settings header shows firebase and firestore; the project id is yours.
    2. Create a test challenger with your own alternate email; confirm the set-password email arrives and the link lands on /login.
    3. Count the accounts you will create. More than about a hundred in one day needs the Blaze plan on the Firebase project before you import.
    4. Create one instructor account and sign in as them; create an interview session; open it as the test challenger; ask one question and see a reply.
    5. Save a personal Groq key on the test account and confirm it is accepted; remove it.
    6. Hide the scenarios you are not running.
    7. Build the cohorts from the rosters with New cohort from a pasted list.
    8. Send the instructor guide to instructors and the challenger guide to the class.
